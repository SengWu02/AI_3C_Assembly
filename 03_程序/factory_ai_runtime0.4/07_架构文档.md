## 一、这是什么

**一句话**：一条用 Factory IO 当被控现场、用 Python 通过 Modbus TCP 当控制器的
3C 产品装配产线，产线上挂了一个本地 LLM 当"线长"。

**它解决什么问题**：

| 层次 | 干的事 |
|---|---|
| 设备控制 | 把 5 个工位的机械动作串成一件产品的完整流程 |
| 状态监视 | 实时把每件产品的判定、节拍、良率显示出来 |
| 质量统计 | 良品 / 不良 / 漏料 三分类计数，算出真实良率 |
| 人工介入 | 界面上可以直接停线、暂停、改节拍 |
| 智能调度 | LLM 看状态给建议，在护栏内自动调节拍 |

**它不解决什么问题**（重要，避免误解）：

  · 不是连续生产。当前是"单件串行"——一件走完全程才做下一件。
    理论上限是最慢工位（约 13s），实际节拍约 45~50s。
    改造方案见 [06_连续生产改造方案.md](06_连续生产改造方案.md)。
  · 不是真实 PLC。Factory IO 是仿真，没有真实 I/O、没有安全回路。
  · LLM 不做决策执行。它给建议，实际动作由代码在护栏内执行。

## 二、整体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        现场（Factory IO 仿真）                    │
│   Emitter  皮带0/2/3  转盘A/B  机械臂×2  视觉0/1  推杆           │
└────────────────────────────┬────────────────────────────────────┘
                             │ Modbus TCP (502)
                             │   Coil 0x     = 输出（开皮带/转盘/夹爪/推杆）
                             │   Input 1x    = 输入（限位/视觉/Moving 信号）
                             │   Holding 4x  = 机械臂位置设定点
                             │   Input Reg 3x= 机械臂实际位置（反馈）
┌────────────────────────────┴────────────────────────────────────┐
│                      modbus_client.py                            │
│   统一接口 + 线程锁（RLock）  ──  modbus 真机 / virtual 假 PLC     │
└────────────────────────────┬────────────────────────────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
┌───────┴────────┐  ┌────────┴────────┐  ┌────────┴─────────┐
│   production   │  │   llm_line      │  │  arm_pos_sampler │
│   _loop 线程    │  │   _leader 线程   │  │  位置采样线程      │
│                │  │                 │  │                  │
│ produce_one()  │  │ 每 90s 分析一次   │  │ 每 0.5s 读位置    │
│  步骤1~5        │  │ 给建议/调节拍     │  │ 写 arm_pos.log   │
└───────┬────────┘  └────────┬────────┘  └──────────────────┘
        │                    │
        │   ┌────────────────┘
        │   │  （都通过线程安全队列投递，不直接碰控件）
        ▼   ▼
┌─────────────────────────────────────────────────────────────────┐
│                      dashboard.py（主线程）                        │
│   画布布局 + 步骤进度 + 节拍趋势 + 事件日志 + 人工介入面板          │
│   _tick 每 200ms 消费队列 → 刷新界面                              │
└─────────────────────────────────────────────────────────────────┘
```

**设计上的一条硬规矩**：

> 工作线程【只能往队列里塞数据】，绝不直接操作 Tk 控件。
> 因为 Tkinter 不允许其他线程碰它 —— 连 root.after() 都不行，
> 违规会抛 "main thread is not in main loop"，表现是【界面完全不刷新】。

## 四、一次生产的完整流程

`produce_one()` 是核心函数，一件产品从头走到尾。

```
步骤1  转盘A 接料 → 送料到皮带2                                   约 13s
       双臂同时回零（初始化）
       转盘A 转 90°（保持不放）
       发料器 + 皮带0 + 滚轮 把料拉进转盘中心
       停滚轮和发料器，皮带0 再多转一会儿（BELT0_EXTRA_TIME）
       转盘A 松手回 0°
       滚轮 + 皮带2 把料送到锁螺丝工位

步骤2  锁螺丝臂搬运到转盘B                                       约 9s
       Z 下接触 → Z 提起 → X 伸到转盘B 上方 → Z 下放料
       夹爪开/合；做完回零

步骤3  点胶臂点胶 + 转盘B 转到 90°                               约 11s
       X 伸到点胶位 → Z 下到工作高度（只下这一次）→ 停留
       做完回零；转盘B 转到 90°（保持不放）

步骤4  转盘B 送料到皮带3                                         约 7s
       转盘B 滚轮推料 → 停滚轮 → 转盘B 松手回 0°
       皮带3 继续走（到 BELT3_RUN_TIME 上限为止）

步骤5  视觉判定 + 分拣                                         约 3~8s
       VISION_1 = True  → 蓝色 → 不良 → 停皮带 + 推杆推出（推到不良仓）
       VISION_1 = False → 绿色 → 良品 → 不停，放行（走到良品仓）
       电平从未变化     → 漏料 → 也算一件，计入总数
```

**返回**：`(is_ok, step_times, stations_passed, verdict)`

## 五、信息流：数据怎么从设备走到界面

```
produce_one() 产生：
    is_ok          本件是否良品
    step_times     各步骤耗时
    stations_passed各工位是否通过
    verdict        三分类：良品/不良/漏料
        │
        ▼
production_loop 汇总：
    verdict_counts  {"良品":n, "不良":n, "漏料":n}
    station_stats   各工位统计（含 ok_kind/ng_kind/miss_kind）
    climb_log       每件一行的爬坡日志（落盘成 climb_log_N件.json）
        │
        ├──► app.update_data(...)   ──┐
        ├──► app.set_step(n)        ──┤  全部往线程安全队列塞
        ├──► app.log(...)           ──┤
        └──► event_manager.add_event ─┘（通过 sink 挂到 app.log）
                                      │
                                      ▼
                          主线程 _tick（每 200ms）
                            _drain_queue() → 应用到控件
```

## 六、线程模型

| 线程 | 干什么 | 碰 Modbus？ | 碰 GUI？ |
|---|---|---|---|
| **主线程** | Tkinter 事件循环 + `_tick` | 否 | **只有它能碰** |
| **production_loop** | `produce_one()` 主流程 | 是（主要） | 只投队列 |
| **llm_line_leader** | 每 90s 调 LLM 分析 | 是（少量） | 只投队列 |
| **arm_pos_sampler** | 每 0.5s 采样机械臂位置 | 是（读） | 否 |

**两条保护**：

1. **Modbus 线程锁**：`modbus_client.py` 里所有 13 个方法都套了 `RLock`。
   `pymodbus` 客户端不是线程安全的，不加锁会"请求/响应错位"——
   读到别人的返回值，现象很诡异（没写的线圈自己动了）。

2. **GUI 更新队列**：工作线程只 `put`，主线程 `get`。见第二节的硬规矩。

## 七、LLM 线长：能干什么、边界在哪

### 实测能力（`test_llm_capability.py`，模型 gemma3:4b）

| 任务 | 结果 | 耗时 |
|---|---|---|
| 产量目标解析（"做50个" → 50）| 3/3 正确 | 4s |
| 产线状态评估（输出合法 JSON）| 3/3 正确 | 12~15s |
| 异常识别（指出问题工位）| 3/3 正确 | 30~39s |

### 它的实际权限

**能做**：
  · 读产线状态（产量、良率、效率、各工位统计、近期事件）
  · 给一个 assessment（正常 / 需要优化 / 异常）
  · 建议动作（continue / alarm_on / alarm_off / stop / rotate）
  · 建议调节拍

**不能做**：
  · 直接控制设备（所有动作由代码执行，且有护栏）
  · 一步把节拍调飞（单次限幅 `LLM_CYCLE_MAX_STEP`，再夹到区间）
  · 改其他任何参数（只开放了节拍这一个旋钮）

### 为什么是"模型判断 + 代码翻译人话"

4B 模型输出自由文本容易跑偏、幻觉；但它输出 JSON 很稳。所以分工：
  · 模型负责**判断**（它的强项）
  · 按固定 JSON 格式回来
  · `_llm_decision_to_human()` 把结果翻译成人话 → **措辞永远可控**

界面显示成：

    产线需要优化｜已生产 24 件（良品 18、不良 5、漏料 1）；
    良率 75.0%；效率 1.2 件/分；动作：继续生产；节拍压快：3.0s → 2.5s

### 怎么关掉它

```python
# config.py
LLM_ENABLED = False      # 关掉后节拍固定，不再由 LLM 调整
```

调试产线时**建议关掉**：否则节拍被它改来改去，
你会分不清某个变化是代码带来的还是 LLM 带来的。

## 八、I/O 模型与口径约定

### 寄存器数值的含义

`ScaleFactor = 1000`，所以**寄存器值就是毫伏**，`10000 = 10.0V`。

```
值 = 0      → 原点侧（X 缩回 / Z 抬起，最高）
值 = 10000  → 极限侧（X 伸出 / Z 下降到最低）
```

### 容易搞反的地方（都踩过）

| 项 | 正确口径 | 踩坑记录 |
|---|---|---|
| 转盘线圈 | 写 `True` → 转到 90° 并保持；写 `False` → **立刻回 0°** | 「松手」本身就是回 0° 命令，所以要先保持住、等料进出完再松 |
| 视觉1 | `True` = 蓝色 = **不良**；`False` = 绿色 = **良品** | 早期代码写成 `True`=OK，导致全部判 NG |
| 机械臂命名 | Python `ARM2` = 现场 `Pick&Place 2` = 锁螺丝位；Python `ARM0` = 现场 `Pick&Place 0` = 点胶位 | 场景里是 0/2，代码里是 1/2，命名错位 |
| Moving 信号 | 写完之后它**可能提前落下**，轴还在继续跑 | 只等信号会在轴走一半时就往下执行 |

### 良率怎么算

```
良率 = 良品数 / (良品 + 不良 + 漏料)
```

**★ 漏料也算一件**。料根本没到视觉位，如果只统计"看到的那些"，
良率会被算高 —— 数字好看但不对。

## 九、关键设计决定（以及为什么）

### 1. 为什么回零要"先轻微前伸一下"

机械臂是速度控制、不是位置闭环。如果它已经贴着原点，直接写 0
等于什么都没做，机构可能纹丝不动 —— 位置就从上一轮的残留状态开始，
逐件累积偏移，最后表现为"下个周期把伸出极限当成了原点"。
先给一个轻微前伸（`ARM_HOME_PRESTRETCH`）把它"唤醒"，再写 0，才真回得去。

### 2. 为什么"等轴真正停稳"要读位置反馈

实测（`test_z_moves.py`）：`reg3` 写 8000 时，Moving 信号在位置 7441
就落下了，但轴随后还在继续跑（7627 → 7874）。
只等信号的话，程序会在轴只走了一半时就往下执行，
"轴自己继续跑"看起来就像"机械臂多做了一个动作"。
所以动作后要读位置反馈，连续 N 次读数相同才算停稳。

### 3. 为什么把两个臂的回零改成并行

两臂是**独立**的执行机构，各有自己的寄存器和 Moving 信号，
可以同时下发命令、并行等待 —— 时间直接减半（6.8s → 3.4s）。
★ 省下的是"第二个臂那一整套 SETTLE + HOLD"，
  `ARM_HOME_SETTLE` 本身不用改小（它是等机械动作完成的绝对时间）。

### 4. 为什么"漏料"要单独分类

`VISION_1 = False` 在"绿料经过"和"根本没有料"两种情况下都成立。
一读到 False 就判良品 → **漏料被算成良品，良率虚高**。
所以加了"电平变化次数"计数：没变化过就判漏料。

### 5. 为什么人工停线不用 emergency_stop 变量

`SafetyManager.evaluate()` 每个循环都会跑，末尾有 `emergency_stop = False`
（"没检测到卡堵就自动复位"）。人工停线如果用同一个变量，
下一轮就被自动清掉 —— 按了没用。所以人工状态单独放。

### 6. 为什么"暂停"只在件与件之间生效

件走到一半暂停，工件会停在奇怪的位置（可能压在传感器上、
可能卡在两个工位之间），恢复时状态很难对。所以在主循环的
件与件之间检查暂停标志 —— 当前件做完才停。
**紧急停线是例外**：它会立刻关设备，因为那是安全动作。

## 十、怎么改（常见需求）

| 想做的事 | 改哪里 |
|---|---|
| 某个机械臂位置不对 | `config.py` 的 `ARM1_X_TARGET` / `ARM1_Z_WORK` / `ARM2_Z_WORK` 等 |
| 某个等待时间不够 | `config.py` 对应的时间常数（都有注释说明调大调小的方向）|
| 加一个新设备 | 先在 `config.py` 加地址常量，再 grep 一遍有没有撞车 |
| 改界面布局 | `dashboard.py` 的 `_build_ui` / `_build_step_panel` |
| 加一个人工按钮 | 在 `_build_manual_panel` 加按钮，`main.py` 里挂回调 |
| 改 LLM 的提示词 | `main.py` 的 `run_llm_line_leader` 里那个 prompt |
| 换个 LLM 模型 | `config.py` 的 `LLM_MODEL`（改完先跑 `test_llm_capability.py`）|

## 十一、边界与已知限制

| 限制 | 说明 | 有没有解 |
|---|---|---|
| **单件串行** | 一件走完全程才做下一件，设备大量空闲。理论 13s，实际 45~50s | 有，见 `06_连续生产改造方案.md` |
| **没有"工位有料"信号** | 漫反射是假的、机械臂 Item Detected 没接线。流水线化必须先解决这个 | 需要在场景里加真实传感器 |
| `ALARM_COIL = 20` 越界 | 场景里 Modbus 输出只映射到 15 号，写报警是空操作 | 改到空闲的 BitOutput（10/11/13/14）|
| 工位1~3 良率恒 100% | 目前只有工位4 有真实判定，其余按"动作走完即通过"记 | 需要加检测手段 |
| `ARM2_Z_WORK` 等位置值靠试 | 没有机械臂位置反馈的绝对标定，是按现象调的 | 见 `test_arm_calibrate.py`（注意标定要避开碰撞）|
| LLM 有随机性 | 同一状态三次给出不同 cycle_time | 已加单次限幅 + 区间夹紧 |
